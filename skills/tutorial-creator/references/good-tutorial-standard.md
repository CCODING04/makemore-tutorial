# 好的教程标准（Good Tutorial Standard）

> 本文档定义了"好的教程"的完整标准。所有教程的创建、优化、审查都必须依据本文档进行评分。

## 核心公式

```
好的教程 = 骨架（Skeleton）+ 血肉（Flesh）+ 灵魂（Soul）
```

---

## 一、骨架（Skeleton）— 清晰结构

### 1.1 学习目标

**要求：**
- 每章必须有 3-5 个学习目标
- 使用动词开头：理解、掌握、能够、识别、解释、画出、配置
- 目标必须具体可衡量（不是"了解 XXX"，而是"能够解释 XXX 的原理"）

**评分标准：**
- ⭐⭐⭐⭐⭐：目标具体、可衡量、有动词开头、3-5 个
- ⭐⭐⭐⭐：目标基本具体，但有1-2个不够可衡量
- ⭐⭐⭐：目标存在但过于笼统
- ⭐⭐：目标缺失或不可衡量
- ⭐：无学习目标

**示例：**
```markdown
## 学习目标

完成本章后，你将能够：

- ✅ **理解** RL 后训练在 LLM 链路中的位置和价值
- ✅ **手写** RLVR 奖励函数（\boxed / #### / 最后数字的抽取链）
- ✅ **解释** GRPO 的数学原理和"全对组优势全零"现象
- ✅ **画出** 从手写 GRPO 到 verl 三角色架构的映射图
```

### 1.2 前置知识

**要求：**
- 分三级：必须掌握、建议掌握、可选
- 每级都要有具体章节链接
- 说明为什么需要这个前置知识

**评分标准：**
- ⭐⭐⭐⭐⭐：三级分类清晰，有链接，有说明
- ⭐⭐⭐⭐：有分类但链接或说明不完整
- ⭐⭐⭐：有前置知识但未分级
- ⭐⭐：前置知识不完整
- ⭐：无前置知识

### 1.3 章节导航

**要求：**
- README 必须有完整的章节导航表
- 每章必须有"下一步"指引
- 形成闭环（从哪来 → 现在在哪 → 到哪去）

**评分标准：**
- ⭐⭐⭐⭐⭐：导航完整，有表格，有链接，形成闭环
- ⭐⭐⭐⭐：导航基本完整，但缺少部分链接
- ⭐⭐⭐：有导航但不完整
- ⭐⭐：导航混乱
- ⭐：无导航

### 1.4 格式一致

**要求：**
- emoji 标记使用一致：🔑 关键概念、⚠️ 警告/陷阱、💡 洞察/技巧、📝 笔记/补充
- 代码块有语法高亮（```python、```bash）
- 层级清晰（# → ## → ### → ####）

**评分标准：**
- ⭐⭐⭐⭐⭐：格式完全一致，emoji 使用规范
- ⭐⭐⭐⭐：格式基本一致，偶有不规范
- ⭐⭐⭐：格式有明显不一致
- ⭐⭐：格式混乱
- ⭐：无格式

## 二、血肉（Flesh）— 内容深度

### 2.1 理论背景

#### 2.1.1 问题引入

**要求：**
- 回答"为什么需要这个技术？"
- 从痛点切入，说明没有这个技术会怎样
- 用类比帮助理解

**评分标准：**
- ⭐⭐⭐⭐⭐：痛点清晰，类比恰当，直击核心
- ⭐⭐⭐⭐：有痛点但类比不够直观
- ⭐⭐⭐：有问题引入但不够深入
- ⭐⭐：问题引入模糊
- ⭐：无问题引入

**示例：**
```markdown
### 问题引入：为什么 SFT 之后还需要 RL？

SFT 教会模型"模仿"人类示范，但有两个根本限制：

1. **覆盖率问题**：人类示范只能覆盖一小部分可能的输入空间
2. **优化目标问题**：SFT 优化的是"模仿人类"，而非"解决问题"

> 💡 **类比**：SFT 像是看教学视频学游泳，RL 像是自己下水练习。
```

#### 2.1.2 数学推导

**要求：**
- 公式必须逐步推导，不是只给最终结果
- 每步都要有解释
- 说明公式的直觉含义

**评分标准：**
- ⭐⭐⭐⭐⭐：逐步推导，每步有解释，有直觉含义
- ⭐⭐⭐⭐：有推导但部分步骤解释不够
- ⭐⭐⭐：有公式但推导不完整
- ⭐⭐：只有公式无推导
- ⭐：无数学内容

#### 2.1.3 历史脉络

**要求：**
- 列出关键技术的演进路径
- 附关键论文链接
- 说明每个阶段的改进点

**评分标准：**
- ⭐⭐⭐⭐⭐：演进路径清晰，有论文链接，有改进说明
- ⭐⭐⭐⭐：有演进路径但论文链接不完整
- ⭐⭐⭐：有历史但不系统
- ⭐⭐：历史信息零散
- ⭐：无历史脉络

### 2.2 代码解释

#### 2.2.1 逐行注释

**要求：**
- 每个函数都要有 docstring（Args/Returns/Steps）
- 关键代码行都要有注释
- 解释"为什么这样写"而非"这行做了什么"

**评分标准：**
- ⭐⭐⭐⭐⭐：每行都有注释，解释"为什么"
- ⭐⭐⭐⭐：大部分有注释，但部分缺少"为什么"
- ⭐⭐⭐：关键行有注释
- ⭐⭐：注释零散
- ⭐：无注释

#### 2.2.2 数据流追踪

**要求：**
- 标注每个变量的 shape/type
- 用 ASCII 图展示数据流
- 标注关键转换点

**评分标准：**
- ⭐⭐⭐⭐⭐：每个变量都有 shape/type 标注，有 ASCII 图
- ⭐⭐⭐⭐：关键变量有标注，但不够系统
- ⭐⭐⭐：部分变量有标注
- ⭐⭐：标注零散
- ⭐：无标注

**示例：**
```markdown
数据流：
    response(str) → 正则匹配 → pred(str) → float(pred) → 比较 → reward(float)

形状变化：
    输入: (batch, seq_len, d_model)
      ↓ Linear
    Q: (batch, seq_len, d_model)
      ↓ Reshape
    Q: (batch, seq_len, heads, d_k)
```

#### 2.2.3 实测输出

**要求：**
- 必须是脚本的真实输出，不是假设的
- 标注测试环境（如"4090，512³ fp32"）
- 解释输出的含义

**评分标准：**
- ⭐⭐⭐⭐⭐：真实输出，有环境标注，有解释
- ⭐⭐⭐⭐：真实输出但缺少环境标注
- ⭐⭐⭐：有输出但不确定是否真实
- ⭐⭐：输出不完整
- ⭐：无输出

#### 2.2.4 调试展示（新增）

**要求：**
- 展示常见错误信息
- 解释错误原因
- 提供修复方法

**评分标准：**
- ⭐⭐⭐⭐⭐：有 3+ 个常见错误，每个都有症状/原因/解法
- ⭐⭐⭐⭐：有 2 个常见错误
- ⭐⭐⭐：有 1 个常见错误
- ⭐⭐：提到错误但不详细
- ⭐：无调试展示

**示例：**
```markdown
### 常见错误

#### 错误 1: CUDA out of memory

**症状：**
```
RuntimeError: CUDA out of memory. Tried to allocate 2.00 MiB
```

**原因：** micro-batch 太大，显存不足

**解法：**
```bash
# 减小 micro-batch
actor_rollout_ref.rollout.micro_batch_size=1
```
```

### 2.3 工程实践

#### 2.3.1 性能分析

**要求：**
- 时间复杂度/空间复杂度
- 实测数据（训练时间、显存占用）
- 性能对比表

**评分标准：**
- ⭐⭐⭐⭐⭐：有复杂度分析 + 实测数据 + 对比表
- ⭐⭐⭐⭐：有复杂度和部分实测数据
- ⭐⭐⭐：有复杂度但无实测数据
- ⭐⭐：性能分析不完整
- ⭐：无性能分析

#### 2.3.2 常见陷阱

**要求：**
- 至少 3 个常见陷阱
- 每个陷阱都有：症状 → 原因 → 解法
- 来自真实经验

**评分标准：**
- ⭐⭐⭐⭐⭐：3+ 个陷阱，每个都有症状/原因/解法
- ⭐⭐⭐⭐：2 个陷阱
- ⭐⭐⭐：1 个陷阱
- ⭐⭐：提到陷阱但不详细
- ⭐：无常见陷阱

#### 2.3.3 最佳实践

**要求：**
- 工业界的真实做法
- 配置推荐值
- 选型建议

**评分标准：**
- ⭐⭐⭐⭐⭐：有工业做法 + 配置推荐 + 选型建议
- ⭐⭐⭐⭐：有部分最佳实践
- ⭐⭐⭐：有提及但不系统
- ⭐⭐：零散提及
- ⭐：无最佳实践

## 三、灵魂（Soul）— 教学流程

### 3.1 直觉优先

**要求：**
- 先讲"为什么"再讲"怎么做"
- 先给类比再给公式
- 先给直觉再给细节

**评分标准：**
- ⭐⭐⭐⭐⭐：完全符合直觉优先原则
- ⭐⭐⭐⭐：大部分符合
- ⭐⭐⭐：部分符合
- ⭐⭐：经常先讲细节再讲原因
- ⭐：完全不符合

### 3.2 渐进复杂

**要求：**
- 简单 → 完整 → 工业
- 每一步都建立在前一步基础上
- 不要有突然的难度跳跃

**评分标准：**
- ⭐⭐⭐⭐⭐：渐进清晰，无难度跳跃
- ⭐⭐⭐⭐：基本渐进，偶有跳跃
- ⭐⭐⭐：有渐进但不明显
- ⭐⭐：难度跳跃明显
- ⭐：无渐进

### 3.3 交叉引用

**要求：**
- 连接前面学过的知识
- 说明"这个概念在 Part X 中出现过"
- 形成知识网络

**评分标准：**
- ⭐⭐⭐⭐⭐：大量交叉引用，形成知识网络
- ⭐⭐⭐⭐：有交叉引用但不够系统
- ⭐⭐⭐：偶有交叉引用
- ⭐⭐：交叉引用零散
- ⭐：无交叉引用

### 3.4 动手验证

**要求：**
- 每个概念都有代码验证
- 提供可运行的脚本
- 展示真实输出

**评分标准：**
- ⭐⭐⭐⭐⭐：每个概念都有验证，脚本可运行
- ⭐⭐⭐⭐：大部分概念有验证
- ⭐⭐⭐：部分概念有验证
- ⭐⭐：验证不完整
- ⭐：无验证

## 四、练习与思考

### 4.1 概念检验

**要求：**
- 3-5 个思考题
- 使用 `<details>` 折叠答案
- 答案有多角度分析

**评分标准：**
- ⭐⭐⭐⭐⭐：3+ 题，有折叠答案，答案详细
- ⭐⭐⭐⭐：2-3 题，答案基本完整
- ⭐⭐⭐：1-2 题
- ⭐⭐：题目不清晰
- ⭐：无概念检验

### 4.2 动手实践（新增）

**要求：**
- 需要写代码的练习
- 有明确的验收标准
- 有步骤提示

**评分标准：**
- ⭐⭐⭐⭐⭐：3+ 个动手练习，有验收标准和步骤提示
- ⭐⭐⭐⭐：2 个动手练习
- ⭐⭐⭐：1 个动手练习
- ⭐⭐：练习不清晰
- ⭐：无动手练习

**示例：**
```markdown
### 练习 1: 实现奖励函数

**验收标准：**
- [ ] 正确抽取 \boxed{} 格式
- [ ] 正确抽取 #### 格式
- [ ] 处理千分位逗号

**步骤提示：**
```python
def reward(response, ground_truth):
    # Step 1: 用正则抽取 \boxed{} 中的内容
    # Step 2: 如果没有，尝试 #### 格式
    # Step 3: 如果都没有，抽取最后一个数字
```
```

### 4.3 扩展思考（新增）

**要求：**
- 引导学生探索更深的问题
- 连接其他知识点
- 启发独立思考

**评分标准：**
- ⭐⭐⭐⭐⭐：2+ 个扩展问题，有引导
- ⭐⭐⭐⭐：1 个扩展问题
- ⭐⭐⭐：有提及但不详细
- ⭐⭐：零散提及
- ⭐：无扩展思考

## 五、综合评分

### 评分公式

```
总分 = (骨架 × 0.2) + (血肉 × 0.4) + (灵魂 × 0.2) + (练习 × 0.2)
```

### 评分等级

| 等级 | 分数 | 说明 |
|------|------|------|
| ⭐⭐⭐⭐⭐ 优秀 | 4.5-5.0 | 可直接发布 |
| ⭐⭐⭐⭐ 良好 | 3.5-4.4 | 需要小幅优化 |
| ⭐⭐⭐ 合格 | 2.5-3.4 | 需要较大优化 |
| ⭐⭐ 待改进 | 1.5-2.4 | 需要重写 |
| ⭐ 不合格 | 0-1.4 | 需要重新设计 |

### 各维度权重

| 维度 | 权重 | 说明 |
|------|------|------|
| 骨架 | 20% | 结构清晰是基础 |
| 血肉 | 40% | 内容深度是核心 |
| 灵魂 | 20% | 教学流程是灵魂 |
| 练习 | 20% | 动手实践是关键 |

## 七、常见问题

### Q: 学习目标用"了解"可以吗？

A: 不推荐。"了解"不可衡量，建议用"理解"、"解释"、"手写"、"画出"等动词。

### Q: 数学推导必须完整吗？

A: 是的。公式必须逐步推导，不能只给最终结果。但可以省略显然的步骤（如代数化简）。

### Q: 调试展示必须有吗？

A: 是的。常见错误和修复方法是教程的重要组成部分，能帮助学生避免踩坑。

### Q: 动手实践必须有吗？

A: 是的。概念检验题只能测试理解，动手实践才能测试掌握。两者缺一不可。

### Q: 如何判断是否达到"良好"标准？

A: 总分 ≥ 3.5，且血肉维度 ≥ 3.5（内容深度是核心）。
