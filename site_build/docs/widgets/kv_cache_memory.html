KV Cache 显存计算器：长上下文为什么烧钱

KV显存 = 2 · L · H_kv · d_head · S · B · bytes。调层数 L、KV 头数 H_kv、批次 B、序列长度 S，看显存随上下文长度的爬升（横轴对数刻度：512 → 64k；下方为关键刻度读数）。

📌 这张图画什么

自回归生成的每一步都要为已经生成的所有 token 保留 K/V 两个矩阵，供后续注意力回看——这就是 KV Cache。它的体积与序列长度 S 成正比、永不封顶：横轴从 512 拉到 64k（对数刻度），纵轴显存。曲线形状告诉你"为什么 128k 上下文的模型服务成本高得吓人"。

🔖 符号与标识符

2K 和 V 两个矩阵——系数 2 的来源
L层数：每层独立一份缓存，32 层就是 32 份叠加
H_kvKV 头数：MHA 与 Q 头相等；GQA 分组共享（Llama-3 用 8）直接按比例省
d_head每头维度（× H_kv = 该层 KV 的特征宽度）
S / B序列长度 / 批次：两个线性乘数——batch 翻倍、长一倍上下文，显存都翻倍
bytes每元素字节数：fp16=2，int8 KV 量化=1（服务端常用优化）

🧭 试一试

  • 预设 "7B MHA"：S=32k 时看读数——单个请求就吃掉一大块 24G 卡
  • 点 "Llama-3 GQA（H8）"：同长度显存 ÷4——GQA 是"用 1/4 显存换几乎无损质量"
  • 把 B 拖到 16：注意整条曲线整体上移——并发是显存的乘法项，容量规划必须按 B 峰值算
  • 切 int8：曲线整体减半——KV 量化是最便宜的"续命"手段
