KV Cache 显存计算器：长上下文为什么烧钱

KV显存 = 2 · L · H_kv · d_head · S · B · bytes。拖滑条看蓝色当前曲线相对两条参照系怎么动：灰虚线 = 7B MHA 基线（L32/H32/d128/fp16/B1，永远不动），红色横线 = 常见显卡的显存上限——蓝线碰到红线 = OOM。

📌 这张图画什么

自回归生成的每一步都要为已经生成的所有 token 保留 K/V 两个矩阵，供后续注意力回看——这就是 KV Cache。它的体积与序列长度 S 成正比、永不封顶。图里三条参照：蓝线是当前配置的显存-S 曲线；灰虚线是 7B MHA 基线（固定不动，用于对比）；红色横线是 24/48/80GB 显卡的显存上限——蓝线在红线之上就是 OOM，交点读出"这张卡最多撑多长上下文"。

🔖 符号与标识符

2K 和 V 两个矩阵——系数 2 的来源
L层数：每层独立一份缓存，32 层就是 32 份叠加
H_kvKV 头数：MHA 与 Q 头相等；GQA 分组共享（Llama-3 用 8）直接按比例省
d_head每头维度（× H_kv = 该层 KV 的特征宽度）
S / B序列长度 / 批次：两个线性乘数——batch 翻倍、长一倍上下文，显存都翻倍
bytes每元素字节数：fp16=2，int8 KV 量化=1（服务端常用优化）

🧭 试一试

  • 预设 "7B MHA"：蓝线与灰基线重合（它就是基线本身）；读数④：24GB 卡上限 S≈48k——单请求几乎吃满一张 4090
  • 点 "Llama-3 GQA（H8）"：蓝线整体掉到灰线的 1/4——同一张 24GB 卡从 48k 撑到 64k 以上，这就是 GQA 的工程价值
  • 把 B 拖到 8：蓝线成倍上跳、提前穿过红线——并发是显存的乘法项，容量规划按 B 峰值算
  • 切 int8：蓝线整体减半——KV 量化是最便宜的"续命"手段；读数④的上限 S 直接翻倍
