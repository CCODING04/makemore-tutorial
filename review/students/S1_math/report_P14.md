## 卡点清单（按严重度排序）

1. 【算式步骤错误】02 章"数学推导"Step 2：
   `浪费 = 16 - (512 % 16) = 16 - 0 = 0 tokens`。
   按这个公式 16 − 0 = **16**，不是 0——教程用错误的步骤得出了（碰巧）正确的结论。
   根因是公式本身在整除情形下失效，正确写法应为 `浪费 = ceil(used/16)×16 − used`
   （本例 32×16 − 512 = 0）。我在这行卡了约五分钟，反复怀疑自己数学不行——后来确认
   是教程错。另外 used=512 恰好被 16 整除，这个例子**展示不出"最后一块的内碎片"**，
   和同章"只剩 ~5%（论文口径 <4%）"的说法互相矛盾（例子里是 0%）。
2. 【公式缺席】02 章标题叫"PagedAttention 的**显存**优化"，却只有"比例账"（75%→0%），
   没有 KV 显存**绝对量**算式 `2 × layers × kv_heads × head_dim × seq × batch × bytes`。
   LLaMA-7B fp16 seq2048 = 1.07GB 这个数字例只出现在 assignment 题 2。
   我自答时只能靠自己默写公式再验算：2×32×32×128×2048×2 B = 1.074 GB ✓。
   比例和绝对量是两回事：0.5B 模型 KV 很小分页不痛，7B 才痛——不讲绝对量，
   "为什么需要 PagedAttention"的动机就少了一半。
3. 【没讲透】PagedAttention 的**块表**思想：全文只有表格里"PagedAttention 块表"四个字
   和"# GPU blocks 是页表容量"一句注释。逻辑块号→物理块号的映射长什么样、
   逻辑块不连续时注意力为什么还能算对、prefix caching 怎么靠"多个请求指向同一物理块"
   省显存——都没有。我靠回忆操作系统分页才把费曼三段补齐（见下），教程自身给不了。
4. 【公式缺席】投机解码**验证概率**：02 章只有"α≈0.60"和"日志里的 acceptance rate"两个孤数，
   接受 k 个的概率 α^k(1−α)、期望产出 E=(1−α^{γ+1})/(1−α)（等比级数）都不在正文。
   我自答验算：E(0.6, 4) = (1−0.6⁵)/0.4 = 2.3056 ✓、α=0 → 1（全拒白赚 1 个）✓、
   α=1 → γ+1=5（0/0 极限）✓——但这套账全部来自 assignment 题 4，教程 02 章让读者
   去对比 acceptance rate，却不告诉读者这个数从哪来。
5. 【口径含糊】TPOT 出现两种口径并存：01 章公式块写 `TPOT = (t_last − t_first)/(n−1)`
   （流式口径），"可操作定义"块又写 `(总时间 − TTFT)/(n_tokens − 1)`（脚本口径）。
   脚本实际是后者：分子减掉的 TTFT 来自**另一次** `max_new_tokens=1` 的独立探测——
   那次探测要**重新做一遍 prefill**（KV 不复用），严格说和同一次生成里的 t_first 不是一个
   东西。偏差方向（prompt 短时偏小）没人点破。我对照脚本和公式时懵了一阵才对上。
6. 【环境坑】新版 transformers（4.57）加载 tokenizer 时会联 huggingface.co 做
   `_patch_mistral_regex` 在线检查，本机代理不可达直接 `ProxyError` 崩溃。
   权重明明已缓存。必须 `HF_HUB_OFFLINE=1` 才能跑。教程/脚本 docstring 只说
   "需要 HF 下载 ≈1GB"，对"已缓存但离线"场景零提示。
7. 【小问题】① README 与 01 章的"数学推导"块逐字重复（Step 1/2/3 一字不差）；
   ② 02 章"错误 1"解法里 `pip install vllm --extra-index-url .../cu118` 疑似过时
   （新版 vLLM 的 wheel 已不这样发，未联网验证，仅存疑）。

## 费曼自检：PagedAttention（直觉 → 公式 → 数字）

- **直觉**：naive 方案像给每个请求预钉死一条连续的大走廊（max_seq_len 长的 KV 区），
  人没来齐走廊空着；PagedAttention 学操作系统分页——KV 切成 16 token 一块的"标准间"，
  池子里统一管理，请求按需借房，手里只拿一张**块表**（逻辑第 0,1,2 块 → 物理第 7,3,9 块）。
  逻辑上连续、物理上离散；两个请求前缀相同就让块表指向同一批物理间（prefix caching）。
- **公式**：每 token KV 字节 = `2 × L × H_kv × d_head × bytes`（K、V 各一份）；
  s 个 token 需 `ceil(s/16)` 块，碎片 = `块数×16 − s`；
  池子总块数 = 可用显存 ÷ 每块字节（即日志 `# GPU blocks`）。
- **数字**：Qwen2.5-0.5B（L=24, H_kv=2, d_head=64, bf16）→
  2×24×2×64×2 B = 12,288 B ≈ 12 KB/token，一块 16 token ≈ 192 KB。
  s=520 → 33 块装 528 位 → 碎片 8 token ≈ 1.5%（分页后）；
  naive 按 2048 整块预留、实际用 520 → 浪费 75%（分页前）。
  放大到 7B：512 KB/token → 64 并发 × 2048 需 ~67 GB，24GB 卡直接爆 →
  "KV 先爆、PagedAttention 救场"的动机就有了数字体感。
- **诚实声明**：三段里"块表之后 attention kernel 怎么按物理块 gather KV"我只能答到
  "kernel 拿块表去取"，再深就答不出——教程没讲，也没告诉我去论文哪一节补。
