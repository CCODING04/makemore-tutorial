## 白板默写自测（不查资料，写完才对答案）

1. **层级 + 2D 索引换算** ✅：grid 含多个 block；block ≤1024 thread、被整体分到一个 SM（不跨 SM）；warp = 32 个连续 thread 锁步执行，是 SM 真正的调度单位；硬件映射 thread→lane/core、warp→SM 调度单元、block→SM、grid→整卡。2D 换算：`col = blockIdx.x*blockDim.x + threadIdx.x; row = blockIdx.y*blockDim.y + threadIdx.y; idx = row*N + col`（row-major）。代入验证：blockIdx=(3,2), threadIdx=(1,5), blockDim=(32,32), N=512 → col=97, row=69, idx=69*512+97=35425。与作业题 1 的 `global_index_2d((0,0),(1,2),(32,32),512)→(2,1,1025)` 同构一致。
2. **coalesced 为什么快** ✅：warp 锁步访存，32 个相邻地址被合并成最少 1 次 128B 事务；坏映射 32 地址分散 → 最多 32 次事务，带宽利用率 1/32。实测 8.4×（对齐后事务数差异 + 路径开销，非满 32×，面试要能解释"理论上限 32 倍、此负载实测 9 倍"的差距来自 L2 命中与计算重叠）。
3. **FA online rescale** ✅：softmax 需整行 max 与分母但行装不下 SMEM → 三个状态跨块滚动：`m`（运行 max）、`l`（运行分母）、`acc`（未归一化输出）。新块到来：`m_new=max(m, m_blk)`；旧部分和按新基准重缩放 `acc←acc·exp(m−m_new)`、`l←l·exp(m−m_new)+rowsum(exp(S−m_new))`；`acc+=P@V`；最后 `acc/l`。代价是每个新块都重缩放历史（FA2 优化的正是这部分 FLOPs），收益是永不物化 T×T、HBM 往返从"读 Q/K/V + 写中间 + 读回"降为每矩阵一次。causal 三阶段：带外块直接跳过 / 对角块逐元素 mask / 下方全算。
4. **48KB SMEM** ⚠️ 如实记：写不出教程出处（教程确实没写），只能答外部知识（默认 48KB/block，Ampere+ 可 opt-in 到 100KB+（4090 上 100KB））。这是教程缺口不是我的缺口。

结论：3.5/4 能默写，缺的那半条正是教程覆盖缺口（K6）。

## 只改 3 件事

1. **改 roadmap L600 口径**："Triton 内核 ≥ SDPA 最优后端 105%" → "≥ SDPA 最优后端 **85%（优秀线）**，共享卡实测 90%~128%，空闲卡可超 100%（卡况敏感，见教程 4.4）"。105% 是最好情况的跨卡数字，写进验收线会误伤每一个照着自测的学生。
2. **补两条 roadmap 承担过但正文 0 覆盖的知识点**（教程 01/02 章各加 3 行即可）：SMEM 每块默认 48KB（4090 可 opt-in 至 100KB，`cudaFuncSetAttribute`）；"decode 为什么 memory-bound"（batch=1 单 token：权重读一次只用一次，算术强度 ≈1 FLOP/byte ≪ 82 → 带宽墙，这就是 KV Cache/continuous batching 章节的内核层根基）。
3. **03 章 ncu 坑点补一行 + 08 章自检**：ncu 坑从一种变两种——"普通用户报 ERR_NVGPUCTRPERM（用 sudo）"；"/usr/local/cuda 若指向旧 toolkit，ncu 会**静默失败**出假数字（87000 GFLOPS + WRONG），务必用与驱动匹配的新版 ncu 并核对 Verification: CORRECT"。08 脚本开头加 `shutil.which('ninja')` 自检并提示 `PATH` 修法。

## 最喜欢 3 处

1. **05 章 4.3"教学版为什么能反超（诚实解读）"**：主动交代 LSE 不用写、autotune 恰好选优、小形状开销占比三个原因，还预判"换 D=128/加 backward 会拉开"——这种反吹牛段落是面试防守的现成弹药，教程里罕见。
2. **03 章 SOL 表"Memory=Compute=92.01"这个看起来像 bug 的数字**：我带着怀疑去复现，结果 91.60=91.60 逐格对上——同值是因为两指标都被 L1TEX 管线顶满，DRAM 才 3.3%。一个"可疑处"变成最深的理解点：SOL 表读的是"哪条管线先满"，不是两个字段碰巧相等。
3. **02 章阶梯叙事**："同一个算法，只是线程到数据的映射不同，差 9 倍"+ README"看趋势，别死记数字"的反复提醒——把 benchmark 纪律写进了正文而非脚注。

## 面试资产清单（S3 复述清单·新增）

- **数字组**：naive 4.7K → L5 8.7K → cuBLAS 21.2K GFLOPS（512³ fp32，4090 峰值 82 TF）；coalesced 8-9×；树形归约 vs atomic ≥77×；FA 教学版 = SDPA 最优后端 90%~128%（最慢 90.3%，"优秀"线 85%）；FA naive→tiling 22.2×（T=4096 causal）；融合算子 2.6×；T² 显存：T=4096 bf16 单矩阵 0.5GB。
- **判断框架（链 4 收尾环，已能白板）**：算术强度 = FLOPs/Bytes，对照 roofline 拐点（4090 ≈82 FLOP/byte）分 compute/memory-bound → ncu SOL 看哪条管线先满（注意 Memory 与 Compute 同值时看子行：L1 94% vs DRAM 3%）→ OPT 查 waves（0.1 waves = 先扩规模再优化）。
- **故事点**：ncu 旧版静默出假数字（87000 GFLOPS + WRONG）是我亲手抓到的——"测出来的数字要先过物理直觉"的现成案例；ninja PATH 坑 = "扩展编译三要素：nvcc 匹配 / ninja 在 PATH / 缓存可清"。
- **深挖钩子**：SOL 同值之谜；L2 命中导致的"超 DRAM 峰值带宽"；FA2 优化的 rescale FLOPs 在哪；为什么 SDPA 前向要写 LSE（backward 用）而教学版不用。

**一句话**：这章的数字可以闭眼引用（两次独立实测几乎逐位复现），唯一要改的是 roadmap 那条 105%——它属于另一张卡的那个下午。
